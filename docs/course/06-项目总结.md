## 1 项目概况

### 1.1 项目基本信息

《智慧企业知识财富库系统》是一个面向课程实践的本地 Web 应用。项目以知识文档管理为基础，叠加认证与权限、检索增强问答、知识图谱、收藏、审计、用户与分类管理、系统运维等功能。最终版本为 V2.0，完成日期为 2026-10-29。

| 维度 | 内容 |
|---|---|
| 项目定位 | 软件工程课程大作业，可用于本地运行、演示和测试 |
| 用户角色 | 管理员、普通员工；演示账号均为虚构 |
| 核心业务对象 | 知识文档、分类、标签、部门、密级、问答片段、图谱节点与边、收藏、审计记录 |
| 前端 | Vue 3 + Vite、Vue Router、ECharts |
| 后端 | Flask 3 REST API、SQLAlchemy |
| 数据库 | SQLite |
| 文本处理 | jieba 中文分词、文本切分与相关度排序 |
| 测试 | pytest，当前测试集共 133 条，编制文档时全部通过 |
| 建模与交付 | 10 张 UML 图、前端页面截图、课程文档、运行与提交说明 |

### 1.2 项目背景与目标

课程项目需要一个既能体现完整软件工程过程、又能形成可运行成果的题目。知识管理系统具备文档、权限、检索、问答、图谱和审计等多个典型模块，既能覆盖需求分析与系统设计，也能体现前后端分离、数据建模、算法服务和安全测试。因此选择“智慧企业知识财富库系统”作为课程题目。

项目目标包括：

1. 完成从立项、需求、设计、开发、测试到交付的完整闭环；
2. 实现可鉴权的知识文档库，确保不同角色和部门只能访问授权内容；
3. 在文档基础上实现检索增强问答，做到回答有依据、来源可追溯；
4. 通过知识图谱展示文档、部门、分类和关键词之间的关系；
5. 用收藏、审计、用户与分类管理、系统运维补齐业务和工程支撑；
6. 通过 pytest 自动化测试和过程文档证明结果可重复、可核查；
7. 在单人条件下完成全部角色职责，并保持范围、进度和质量可控。

### 1.3 项目范围与实际边界

本期交付覆盖八个业务与管理模块：认证与权限、知识文档、检索增强问答、知识图谱、收藏、审计、用户与分类管理、系统运维。前端页面、后端接口、数据库模型、测试、10 张 UML 图、前端页面截图和课程文档也属于实际交付范围。

项目没有真实企业用户，也没有在生产环境上线。所有演示制度、账号、部门和图谱数据均为虚构。外部大模型调用只作为可选增强，未配置时系统仍应提供检索、片段来源和本地回答链路。项目没有实现真实企业 SSO、多租户、原生移动端、在线协同编辑、生产级高可用和图数据库平台。

### 2.4 偏差分析与处理

本项目的主要偏差不是业务模块缺失，而是 V2.0 前端技术升级带来的集成工作量增加。前端采用 Vue 3 + Vite 后，需要重新组织页面路由、登录态传递、API 客户端、错误处理、图表加载和构建流程；相较服务端模板方式，前后端联调和页面状态验证需要更多时间。

处理方式如下：

1. 优先保证八个业务模块和核心演示链路，减少与验收无关的装饰性页面；
2. 先固定 API 请求/响应结构和错误处理方式，再并行完善页面；
3. 将前端页面检查与后端接口测试放在同一里程碑，避免最后集中返工；
4. 把 V2.0 技术栈和页面截图纳入文档基线，确保交付材料与实现一致；
5. 对不能在本期完成的生产级能力明确列入范围外和后续改进，不用“已完成上线”掩盖项目边界。

## 3 功能与技术成果

### 3.1 功能成果

#### 3.1.1 认证与权限

系统支持本地账号登录、退出和会话维持，区分管理员与普通员工角色。文档按照公开、内部、机密等可见性规则控制访问；管理员可访问全部文档，机密文档仅允许同部门用户或文档作者访问。无权限访问返回拒绝结果，不在详情、列表、检索或问答来源中泄露正文。关键登录失败也会进入审计，便于发现异常尝试。

权限设计的重点不是只在详情页做判断，而是让文档列表、详情、检索、问答、收藏和统计使用同一套可见性规则。这样能够降低“列表不可见但问答能搜到”的不一致风险。

#### 3.1.2 知识文档

文档模块支持新建、查看、编辑、删除、分类、标签、状态、密级、部门和版本等字段，并提供关键词检索、分类筛选、部门筛选、密级筛选和分页。文档保存后会触发知识片段切分和图谱同步，使后续问答与图谱使用最新内容。文档正文、摘要和元数据在页面中统一展示，便于课程演示和复查。

#### 3.1.3 检索增强问答

问答流程包括问题接收、中文分词、权限范围内的候选文档筛选、知识片段检索、相关度排序、Top-K 选择、来源组装和回答生成。回答页面展示来源文档、部门、片段摘要和相关度，用户能够判断答案依据。系统还保存问答历史，支持查看本人历史记录。无命中时明确说明没有检索到合适依据；未配置外部模型时采用本地回答链路，不把本地结果伪称为大模型生成。

权限先于检索是本项目最重要的设计约束之一。系统先根据当前用户确定可见文档，再在对应片段中检索，避免机密片段进入候选集、日志展示或来源列表。

#### 3.1.4 知识图谱

知识图谱模块将文档、部门、分类和关键词等实体组织为节点与边，通过接口提供给前端，并使用 ECharts 力导向图展示。文档变更后可再次同步关系，管理员可以通过维护入口补充自动同步不足的节点或关系。该模块主要用于表达知识之间的关联，而不是替代图数据库或复杂图计算平台。

#### 3.1.5 收藏、审计与管理

收藏模块支持收藏、取消收藏和个人收藏列表，并通过唯一约束避免重复收藏。审计模块记录登录成功、登录失败、文档访问、问答和关键管理操作，管理员可按条件查询。用户与分类管理模块提供用户查看、用户状态/角色相关维护和分类维护能力，管理入口只对管理员开放。系统运维模块提供工作台、关于页、健康检查、初始化数据、启动/停止和测试脚本，使项目能够在本地复现。

| 层次 | 技术实现 | 设计价值 |

| 文本处理 | jieba、切分、相关度评分、Top-K | 在没有复杂向量平台的前提下提供可解释检索 |
| 测试层 | pytest、测试夹具、临时数据库 | 支持重复执行，避免污染演示数据 |
| 文档与图 | Markdown、PlantUML、10 张 UML、页面截图 | 形成可审阅的设计和交付证据 |

项目没有把业务逻辑写入页面模板或前端组件，而是通过后端 API 统一完成鉴权、权限过滤、数据访问和审计。这一结构使权限规则能够被自动化测试直接覆盖，也减少了前端绕过业务规则的空间。

### 3.3 工程化成果

1. 使用应用工厂、分层路由和服务模块组织 Flask 后端，配置项支持不同运行环境。
2. 使用统一 API 客户端处理前端请求和错误，使认证失效、无权限和服务异常有一致表现。
3. 使用 SQLAlchemy 建立用户、文档、知识片段、图谱、收藏、审计和问答历史等模型。
4. 使用独立临时数据库执行测试，避免测试修改演示数据库。
5. 使用虚构种子数据保证首次启动后即可演示，同时避免真实企业信息。
6. 提供启动、停止、测试和依赖安装说明，降低复查环境搭建成本。
7. 完成 10 张 UML 图和前端页面截图，覆盖用例、时序、活动、状态、类、ER、部署、构件和三层架构等视角。

## 5 各阶段复盘

### 5.1 需求阶段复盘

| 复盘项 | 评价 |
|---|---|
| 有效做法 | 先确定八个模块和范围外清单，再写功能和验收条件；把权限、问答来源和虚构数据边界提前写入需求 |
| 主要不足 | 没有真实企业用户参与，场景主要来自课程目标和合理推演；部分交互细节直到前端联调才完全明确 |
| 改进方向 | 增加低保真原型和角色走查，在编码前用具体页面流程验证需求 |

需求阶段最有价值的决定是明确“先权限、后检索”和“演示数据全部虚构”。前者为后续问答安全提供了硬边界，后者避免课程项目被误解为真实企业案例。需要承认的是，课程项目没有真实用户访谈和真实业务样本，需求覆盖度不能等同于生产系统。

### 5.2 设计阶段复盘

| 复盘项 | 评价 |
|---|---|
| 有效做法 | 采用前后端分离与分层服务；先定义角色、权限和数据关系；用 UML 补充静态与动态视角 |
| 主要不足 | V2 前端技术栈调整后，部分接口字段和页面状态设计需要二次对齐；单人评审容易漏掉边界 |
| 改进方向 | 采用接口契约优先和页面状态表，在开发前固定请求、响应、空状态和错误状态 |

设计阶段形成了 10 张 UML 图，包括用例、登录时序、问答时序、文档发布活动、文档状态、类图、ER 图、部署图、构件图和三层架构图。这些图不只是交付材料，也帮助检查模块边界和调用顺序。问题在于图形设计与实际 V2 前端联调之间存在时间差，后续应把 API 契约和页面状态纳入设计基线。

### 5.3 实现阶段复盘

| 复盘项 | 评价 |
|---|---|
| 有效做法 | 按认证、文档、RAG、图谱、管理逐步增量实现；共享权限和 API 客户端；每个模块完成后立即验证 |
| 主要不足 | 单人开发容易优先完成“能运行”，后补异常边界；前端构建与后端联调占用较多时间 |
| 改进方向 | 继续使用小步提交和接口测试；为前端增加端到端自动化；把异常路径纳入开发完成定义 |

实现阶段的难点集中在权限一致性、RAG 检索可解释性和图谱同步。通过把文档可见性提取为共享规则、在检索前过滤文档、对图谱同步做幂等处理，系统才形成稳定的业务闭环。Vue 3 + Vite 前端使页面组织和交互更清晰，但也暴露出接口契约、登录态和构建配置必须提前设计的问题。

### 5.4 测试阶段复盘

| 复盘项 | 评价 |
|---|---|
| 有效做法 | 使用临时数据库；覆盖权限矩阵和问答边界；测试与演示数据分离；在里程碑前执行全量回归 |
| 主要不足 | 没有统计代码覆盖率；缺少浏览器端端到端自动化；没有生产级性能和并发测试 |
| 改进方向 | 增加覆盖率、E2E、性能基线和持续集成结果归档 |

测试阶段确认了自动化测试对单人项目的重要性。由于没有独立测试人员，权限和问答等高风险区域必须通过可重复用例来补偿人工检查的不足。133 条用例覆盖了 API、安全、RAG、登录和系统主链路，但课程项目没有采集未实现的覆盖率数据，因此不能把“测试通过”扩大解释为所有代码路径均已覆盖。

## 6 遇到的问题及解决方案

| 编号 | 问题 | 根因分析 | 解决方案 | 经验 |
|---|---|---|---|---|
| P-01 | 单人承担全部角色，时间与精力冲突 | 没有多人并行和外部评审 | 用 WBS、周计划、里程碑和 Definition of Done 拆分工作；关键路径优先 | 单人项目更需要书面计划 |
| P-02 | 权限规则容易在不同入口重复实现 | 列表、详情、问答、收藏都有可见性判断 | 建立共享可见性规则；检索前先过滤；用权限矩阵回归 | 安全规则必须集中 |
| P-03 | 问答可能越过文档权限 | 检索候选集未先按用户过滤 | 先确定可见文档，再检索片段；来源也走同一规则 | 问答不是权限例外 |
| P-04 | 业务词分词效果不足 | 通用词典对课程业务词覆盖有限 | 使用 jieba 领域补充词和边界测试，保持打分可解释 | 检索效果要用真实问题集验证 |
| P-05 | 文档变更后图谱不同步 | 图谱与文档分属不同数据路径 | 文档保存触发同步；同步幂等；提供维护与重同步 | 关系数据要有重建机制 |
| P-06 | 测试污染演示库 | 测试直接使用运行数据库 | 测试使用临时数据库和独立夹具 | 测试隔离是质量基础设施 |
| P-07 | 前后端联调字段漂移 | 页面和接口由同一人先后实现，缺少契约检查 | 固定 API 结构，使用统一客户端，补充 API 测试 | 单人也要做接口契约管理 |
| P-08 | 登录失败难以追踪 | 只记录成功登录，缺少失败审计 | 记录失败登录并加入计数窗口和锁定处理 | 安全事件要可观察 |
| P-09 | UML 中文标签显示异常 | 渲染字体和工具配置不一致 | 固定中文字体与渲染流程，逐图校对 | 图也是交付质量的一部分 |
| P-10 | 文档容易落后于代码 | 文档集中到最后阶段编写 | 每阶段同步增量，W11—W12 统一校对版本、路径和截图 | 文档要进入里程碑 |

## 7 项目不足与后续改进

### 7.1 项目不足

1. **没有真实用户和真实生产上线。** 项目是课程设计，需求和场景主要基于课程目标与合理推演，不能证明真实企业采用或产生实际业务收益。
2. **没有生产级部署与高可用。** SQLite 和本地运行方式适合演示，不适合高并发、多实例和长期生产运维。
3. **登录限流和会话能力仍偏演示。** 单机限流、进程内状态和多实例共享等问题没有在本期解决。
4. **RAG 评估不充分。** 已实现检索、排序、来源和历史，但缺少大规模问题集、召回率/精确率评估、重排模型和系统化幻觉评估。
5. **知识图谱能力有限。** 采用轻量关系模型和 ECharts，不具备图数据库查询、复杂推理和大规模图谱分析能力。
6. **测试覆盖仍有缺口。** 133 条用例全部通过是重要成果，但没有采集代码覆盖率，也缺少浏览器端端到端自动化和生产级压力测试。
7. **单人评审的客观性有限。** 虽然使用清单、自动化测试和文档复核，但没有真正的多人代码审查和用户验收。
8. **前端体验和可访问性仍有提升空间。** 主要面向桌面演示，移动端适配、键盘操作、无障碍语义和跨浏览器细节未做系统验证。
9. **文档和实现的一致性依赖人工校对。** 虽然完成了统一校对，但缺少自动检查文档链接、接口字段和截图版本的机制。

### 7.2 后续改进路线

| 优先级 | 改进项 | 具体动作 | 预期价值 |
|---|---|---|---|
| P0 | 可观测性和质量门禁 | 接入持续集成、覆盖率统计、前端 E2E 和统一测试报告 | 让每次变更都有客观回归证据 |
| P0 | 权限安全加固 | 补充细粒度权限、审计异常检测、共享限流存储和会话策略 | 降低越权和暴力尝试风险 |
| P1 | 数据层演进 | 从 SQLite 迁移到 PostgreSQL，引入迁移工具和连接池 | 支持更大规模和更可靠的部署 |
| P1 | RAG 评估与优化 | 建立问题集、召回评估、重排和模型输出评价 | 从“可演示”走向“可度量” |
| P1 | 图谱能力增强 | 引入图数据库或更完整的实体/关系查询能力 | 支持复杂关系分析和探索 |
| P2 | 用户体验完善 | 移动端适配、无障碍、表单校验、操作引导和多语言 | 提升可用性与可访问性 |
| P2 | 生产运维 | 备份恢复、监控告警、密钥管理、容器化与灰度发布 | 为真实部署做准备，但不在课程范围内宣称已完成 |

改进项中，P0 针对当前质量证据的缺口，P1 面向技术和业务深化，P2 属于产品化方向。继续演进时应先明确真实用户和合规要求，再决定是否引入多租户、企业身份认证和外部模型服务。

## 8 个人收获

### 8.1 工程能力

通过独立完成项目，我系统实践了需求分析、架构设计、前后端开发、数据库建模、测试设计和文档交付。尤其是 Vue 3 + Vite 与 Flask 3 REST API 的联调，让我认识到接口契约、错误处理、路由守卫和构建配置不是附属工作，而是系统能否稳定演示的一部分。

### 8.2 项目管理

单人项目没有天然的团队分工，必须自己建立范围、WBS、里程碑和检查点。最大体会是：计划不是把任务列出来，而是明确每个阶段的输出、验收条件和延期处理方式。关键路径优先、每周缓冲、冻结后只修复不扩展，是控制单人项目节奏的有效方法。

### 8.3 质量与安全意识

权限、问答来源、审计和测试隔离让我认识到，安全边界必须通过共享规则和自动化用例来保证。只在某个页面加判断并不可靠；权限规则一旦分散，就很容易在问答、图谱或统计入口出现遗漏。133 条测试用例的价值不只是数量，而是把高风险规则固化为可重复检查。

### 8.4 文档与表达

项目还让我练习了把设计意图写成可检查文档、把过程数据写成可核验表格、把不足和边界写清楚。课程文档不能只描述“做了什么”，还要说明为什么这样做、如何验证、哪些没做以及后续如何改进。

### 8.5 角色切换与自我管理

本人同时承担项目组长和全部成员职责，需要不断在管理者、开发者、测试者和文档编写者之间切换。这个过程提升了任务拆解、优先级判断、风险识别和自我检查能力，也让我更清楚多人项目中沟通、评审和交接为什么重要。
