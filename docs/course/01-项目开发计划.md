## 1 项目背景、目标与范围

### 1.1 项目背景

企业在日常经营中会沉淀制度、流程、产品说明、项目经验和常见问题等知识，但这些内容往往分散在文件夹、聊天记录和个人笔记中。即使已经建立文档库，仍常见三个问题：第一，文档缺少统一分类、版本和状态管理，查找成本高；第二，机密文档与普通文档混放，检索和问答容易越过权限边界；第三，传统关键词搜索只能返回文档列表，用户仍需逐篇阅读并自行整理答案。

本项目以课程大作业为背景，设计并实现一个可本地运行、可重复演示的智慧企业知识财富库系统。系统以“可鉴权的知识文档库”为底座，叠加检索增强问答、知识图谱、收藏、审计、用户与分类管理、系统运维等功能，用于展示软件工程全过程中的需求分析、体系结构设计、模块实现、测试验证和交付管理能力。

需要明确的是，本项目没有真实企业用户，也没有在生产环境上线，不使用真实企业资料。系统中的账号、制度正文、部门、图谱节点和问答记录均为虚构演示数据。项目价值在于验证一套完整的技术与工程闭环，而不是证明某个真实组织已经采用该系统。

### 1.2 项目目标

| 编号 | 目标 | 可检查结果 |
|---|---|---|
| G1 | 完成从立项、需求、设计、开发、测试到交付的完整过程 | 各阶段均有可追溯文档、版本记录和验收证据 |
| G2 | 形成可运行的业务闭环 | 用户能够登录、浏览和检索文档、发起问答、查看图谱，并按照角色和密级访问数据 |
| G3 | 建立清晰的前后端分层架构 | Vue 3 + Vite 前端通过 REST API 调用 Flask 3 后端，业务逻辑不散落在页面中 |
| G4 | 建立可重复的自动化质量基线 | pytest 自动化测试共 133 条，编制本计划时的项目快照为全部通过；正式验收以冻结版本的实际执行结果为准 |
| G5 | 形成完整的课程交付材料 | 包含 10 张 UML 图、前端页面截图、测试证据、运行说明和课程文档 |

### 1.4 项目范围

#### 1.4.1 范围内

| 模块 | 本期范围 | 关键边界 |
|---|---|---|
| 认证与权限 | 登录、退出、会话、角色识别、菜单控制、文档密级与部门隔离 | 采用本地账号体系，不接入企业统一身份认证 |
| 知识文档 | 文档新建、编辑、删除、查看、分类、标签、状态、筛选、分页和检索 | 以文本型知识文档为主，不扩展为完整办公套件 |

| 收藏 | 文档收藏、取消收藏、个人收藏列表 | 仅服务当前登录用户 |

| 用户与分类管理 | 用户查看与管理、分类维护等后台能力 | 账号数据为虚构演示数据 |
| 系统运维 | 工作台、关于页、健康检查、初始化数据、启动与测试脚本 | 以单机演示为主，不承诺生产高可用 |
| 前端与交互 | Vue 3 + Vite 单页应用、路由、API 客户端、统一布局、错误提示和页面截图 | 覆盖桌面端主要页面，不承诺原生移动端适配 |
| 测试与文档 | pytest 自动化测试、UML、需求/设计/测试/总结文档、运行说明 | 以课程验收和可复现性为目标 |

#### 1.4.2 范围外

| 不在本期范围 | 原因 |
|---|---|
| 真实企业生产部署、正式运营和高可用集群 | 课程项目以本地可演示和工程过程验证为目标 |
| 对接真实企业 SSO、LDAP、AD 或多租户组织体系 | 会显著扩大认证与数据隔离范围 |
| 大模型训练、微调、向量数据库平台和模型运营 | 技术风险与资源成本超出课程周期 |
| 原生移动端 App、复杂审批流和在线协同编辑 | 不构成核心验收链路 |
| 生产级备份恢复、合规审计、等保测评 | 需要真实组织和运维环境，课程阶段无法真实完成 |
| 真实企业用户访谈和真实业务数据 | 本项目明确为课程虚构场景 |

### 1.5 约束与假设

1. 项目由一人完成，所有角色由本人兼任，进度和质量控制必须依赖时间盒、清单和自检。
2. 项目采用 Vue 3 + Vite、Flask 3 REST API、SQLAlchemy、SQLite、ECharts、jieba 和 pytest，优先保证本机可复现。
3. 外部大模型接口只作为可选增强；即使不配置外部模型，检索、来源展示和本地回答链路仍应可演示。
4. 演示数据必须为虚构内容，文档、截图和答辩材料不得声称系统已在真实企业生产使用。
5. 所有关键交付物以 2026-10-29 的冻结版本为准；编制计划时的 133 条测试结果视为项目快照，最终验收需重新执行。

## 2 组织与单人角色映射

### 2.1 组织形式

本项目采用“单人独立项目组”形式。本人既是项目组长，也是全部执行角色的承担者。项目组没有其他成员，不存在代码交接、跨人沟通或多人并行开发；但为了保证软件工程过程完整，仍按照课程要求设置需求、设计、开发、测试、配置管理和交付等角色，并由本人以不同工作视角完成对应职责。

这种组织形式的优势是决策链短、文档与代码一致性强、问题定位成本低；主要风险是时间冲突、个人盲区和自我评审不足。因此，计划通过固定自检清单、阶段性冻结、自动化测试和外部课程反馈降低风险。

### 2.4 单人协作机制

| 场景 | 具体做法 |
|---|---|
| 角色切换 | 每周开始先以项目经理视角确认任务，再以开发和测试视角执行，周末以评审视角验收 |
| 自我评审 | 需求、设计、代码和文档分别使用独立检查清单，至少间隔一次任务切换后再复核 |
| 防止范围膨胀 | 所有新增想法先登记，只有不破坏 12 周计划和验收标准时才进入本期 |
| 防止“只开发不验证” | 每个模块完成后立即补接口测试和手工路径，不把测试集中拖到最后一周 |
| 防止文档脱节 | 版本号、模块名、技术栈和截图以冻结代码为准，交付前进行文档与实现对照 |

### 5.3 进度控制规则

1. **周计划只承诺可验证输出。** 不以“完成开发”作为检查点，而以可启动页面、可调用 API、可执行测试或可审阅文档作为输出。
2. **关键路径优先。** 认证与权限、文档、RAG 属于关键路径；图谱、界面细节和文档美化不得挤占关键路径测试时间。
3. **延期先调范围，不先降质量。** 若任务延期，优先压缩非核心视觉优化，再考虑顺延；不得以减少权限测试或跳过回归换取进度。
4. **每周设置缓冲。** 周末预留半天处理缺陷和文档同步，避免问题堆积到 W12。
5. **版本冻结。** W12 只修复阻断验收的问题，不新增业务模块；任何变更需记录影响并重新回归。

### 8.2 版本与命名规则

1. 应用版本采用 `V主版本.次版本`，本项目最终交付版本为 `V2.0`。
2. 文档版本采用 `V0.x` 草稿、`V0.9` 评审稿、`V1.0` 定稿；文档内容发生实质变化时递增版本。
3. 文档文件名保持“编号-名称.md”格式，例如 `01-项目开发计划.md`、`06-项目总结.md`。
4. Git 提交信息采用“类型: 简短说明”，例如 `feat: 完成权限内问答检索`、`test: 补充文档权限矩阵`、`docs: 更新项目总结`。
5. 里程碑使用标签记录，例如 `m3-core-mvp`、`m5-quality-baseline`、`v2.0-course-submit`。

### 8.3 分支与提交策略

单人项目仍保留轻量分支纪律：

| 分支/操作 | 用途 |
|---|---|
| `main` | 保存可运行、可回归的稳定版本 |
| `feature/*` | 单个模块或较大改动，完成测试后合并 |
| `docs/*` | 文档、UML、截图等非运行时代码改动 |
| 小步提交 | 每次提交只解决一个明确问题，便于定位和回退 |
| 合并前检查 | 至少确认应用可启动、相关测试通过、文档无版本冲突 |

### 8.4 变更控制

新增或调整需求时填写变更记录，至少说明变更内容、影响模块、对进度和测试的影响、是否进入本期。W12 冻结后只接受以下变更：

1. 阻断演示或验收的缺陷修复；
2. 与事实不符、可能造成误导的文档更正；
3. 安全检查发现的权限或数据泄露修复；
4. 不改变范围的兼容性修复。

任何冻结后修改都必须重新执行受影响测试，并在项目总结或验收记录中说明。

### 8.5 备份与可复现性

1. 代码、文档、UML 源文件和截图纳入版本管理；本地数据库、日志和缓存不作为交付成果。
2. 交付前确认项目内虚拟环境、依赖清单、启动脚本和测试命令可用。
3. 数据库可以通过初始化脚本重建，演示账号和业务正文使用虚构数据。
4. 对外提交时排除临时文件、密钥、个人环境配置和运行日志。

1. 代码或文档产物已写入规定位置；
2. 接口/页面/文档可通过明确步骤验证；
3. 相关测试已执行并记录结果；
4. 权限和数据边界已检查；
5. 文档中的路径、名称、版本与实现一致；
6. 不引入新的阻断级缺陷，已知限制已记录；
7. 变更已提交并可追溯。

### 9.5 缺陷处理原则

| 等级 | 判定 | 处理要求 |
|---|---|---|
| 阻断 | 无法启动、无法登录、主链路中断、数据泄露 | 立即修复，修复后执行完整相关回归 |
| 严重 | 核心模块不可用、权限结果错误、问答越过可见范围 | 验收前必须修复，并补充回归用例 |
| 一般 | 部分筛选/展示异常、错误提示不清晰、非主链路功能缺陷 | 评估影响，原则上验收前修复 |
| 轻微 | 文案、样式、非关键体验问题 | 可进入已知问题清单，不影响放行 |

## 10 沟通机制

### 10.1 沟通对象与方式

| 沟通对象 | 沟通内容 | 频率/时点 | 方式 | 输出 |

### 10.2 沟通规则

1. 与课程要求相关的问题及时记录，不凭猜测改变交付格式。
2. 任何影响范围、技术栈或验收标准的反馈，都先进入变更记录，再决定是否修改。
3. 演示说明必须明确“课程项目、非生产系统、演示数据虚构”，不把本地演示描述为真实上线。
4. 单人项目也要保留书面记录，避免仅凭记忆安排任务。
5. 发现无法在计划内解决的问题时，优先缩小非核心范围并明确已知限制，而不是隐瞒或夸大完成度。

## 12 验收标准与验收方法

### 12.1 功能验收标准

| 编号 | 验收项 | 通过条件 |
|---|---|---|
| A-01 | 启动与初始化 | 按说明可启动前后端，数据库可初始化，健康检查可返回正常状态 |
| A-02 | 认证与角色 | 正确账号可登录，错误账号有明确提示，退出后会话失效，角色菜单符合权限 |
| A-03 | 文档管理 | 可新建、编辑、查看、删除文档；分类、标签、状态、筛选、分页和检索可用 |
| A-04 | 文档权限 | 管理员、同部门、异部门、作者、未登录场景结果符合权限规则，越权不返回正文 |

| A-06 | 知识图谱 | 页面可显示节点和边，支持拖拽/缩放；文档变更后图谱可同步；管理员可维护 |
| A-07 | 收藏与审计 | 收藏可增删且不重复；关键动作包含失败登录记录；管理员可查询审计 |
| A-08 | 用户与分类管理 | 管理员可查看和管理用户、维护分类；非管理员不能进入管理操作 |

| A-10 | 前端页面 | 登录、工作台、文档、问答、图谱、审计、用户与分类等主要页面可用，截图与版本一致 |
| A-11 | 自动化测试 | 冻结版本执行 pytest，133 条用例的最终实际结果全部通过；若有变化以实际日志为准 |
| A-12 | 交付材料 | 文档、10 张 UML、截图、运行说明、测试证据和交付清单齐全 |

### 12.2 质量验收标准

1. 不存在阻断级缺陷；严重缺陷已修复并有回归证据。
2. 权限、问答来源和审计三类安全相关场景均有专项测试。
3. 测试使用独立数据库，执行后不污染演示数据。
4. 前端可构建，后端可启动，接口路径与文档一致。
5. 文档中的项目版本为 V2.0，技术栈为 Vue 3 + Vite、Flask 3 REST API、SQLAlchemy、SQLite、ECharts、jieba、pytest。
6. 演示数据均为虚构，文档不声称真实企业用户、真实生产上线或真实业务成效。
7. 已知限制明确列出，不用“全部完美”或无法验证的指标替代事实。

### 12.3 验收方法

| 步骤 | 操作 | 记录 |
|---|---|---|
| 1 | 冻结代码、文档、UML 和截图版本 | 版本号、冻结时间、文件清单 |
| 2 | 在独立环境按运行说明安装依赖并初始化 | 安装和启动日志 |
| 3 | 执行 pytest 全量测试 | 总数、通过、失败、错误、耗时、关键输出 |
| 4 | 按主链路手工演示 | 登录、文档、问答、图谱、收藏、审计、管理、健康检查 |
| 5 | 执行权限对照场景 | 管理员/同部门/异部门/作者/未登录结果 |
| 6 | 检查 10 张 UML 和页面截图 | 文件齐全、中文可读、版本一致 |
| 7 | 对照验收表逐项签字或打勾 | 验收通过、有条件通过或不通过 |

### 12.4 验收结论规则

- 全部功能项通过、自动化测试全部通过、无阻断/严重缺陷、交付材料齐全：验收通过。
- 非核心功能存在一般问题，但核心链路完整、权限无泄露、测试通过且问题已记录：可有条件通过，并列出后续修复项。
- 出现无法启动、核心链路中断、权限泄露、测试失败或关键交付物缺失：验收不通过，修复后重新执行验收。

## 13 计划收口

本计划以 2026-10-29 为交付控制点，以 12 周为整体窗口，以八个业务与管理模块、133 条自动化测试、10 张 UML 和前端页面截图为课程交付基线。项目最终是否通过，不取决于计划中写了多少功能，而取决于冻结版本能否按验收表复现、测试结果是否真实、文档是否与实现一致、权限边界是否可靠。

在后续验收中，如实际测试数量、通过结果、页面截图或文档路径发生变化，应更新相应记录并以实际交付物为准。本计划不把课程项目描述为真实企业生产系统，也不将虚构演示数据描述为真实业务数据。
